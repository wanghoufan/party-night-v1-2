# Party Night V2｜09 复核验收与迁移说明

## 一、最终交付范围

- 主线游戏：7 类 × 50 张 = **350 张**
- 可选扩圈模块：**40 张**
- 统一总览 / 底层机制：1 份
- 主线题库：7 份
- 扩圈模块：1 份
- 逐卡开发元数据：`10-卡片元数据.json`
- 本复核说明：1 份

## 二、本轮复核发现并已整改的关键问题

### P0｜Heat 5 与 MATCH 的作用域冲突

旧版把 H5 写成全桌 Heat，但 MATCH 是 pair-level 状态：一对互选成功，并不代表其他人也进入相同关系阶段。

**整改：** Session Heat 只保留 H1～H4；5档改为逐 pair 的双向解锁。

### P0｜题库有规则、但没有逐卡元数据

旧版虽然定义了 `targetMode / consentMode / matchRequired`，350 张卡却只有“编号 / 档位 / 题面”，开发者无法可靠执行规则。

**整改：** 新增 `10-卡片元数据.json`，逐卡补充路由、隐私、同意、信号字段。

### P0｜大冒险终局存在“无交集却自动对视”的同意漏洞

旧版在双方没有共同选项时自动降级为“对视5秒”，仍然执行了双方没有共同选择的动作。

**整改：** 只执行双方勾选交集；无交集直接跳过动作、继续聊天。

### P1｜5档语义不统一

旧版“谁最可能”和“指人游戏”存在大量单向 / 群众判断的5档题，但总规则又定义5档为双向确认。

**整改：**

- 谁最可能：5档 = 0，最高到4档；它只产生 Crowd Signal。
- 指人游戏：公开单向题全部停在4档，只保留秘密互选终局为5档。
- 我从来没有：仅互选终局保留5档。
- 二选一：只有 MATCH pair 专属内容保留5档。

### P1｜“我从来没有”的 Shared Signal 计算错误风险

旧版可能把“都没做过”也当共同经历；高档“今晚有没有某个人”更无法知道目标是谁，却可能被误用于 Pair Score。

**整改：**

- Shared 只统计“做过”的少数共同经历。
- 80%以上都“做过”则不计 Shared。
- 4档今晚私密题不产生 Pair Signal。
- 终局秘密选对象才进入 Personal / Mutual Signal。

### P1｜二选一存在“热门答案 = 假兼容”

如果全桌都选同一个热门答案，旧逻辑会让几乎所有 pair 同时加 Compatibility。

**整改：** 某选项达到80%以上时不计兼容；至少共同回答3道有效题后才产生兼容加权。

### P1｜默契测试低档与二选一同质化

旧版默契1～2档本质是“两个人玩二选一”。

**整改：** 1～2档全部改为“双方先猜对方 → 再揭晓真实答案”，把玩法身份固定为“理解 / 预测对方”。

### P1｜DOUBLE MATCH 是未定义的新状态

旧版默契终局在已 MATCH 的前提下又显示 `DOUBLE MATCH`，但总纲没有这一状态。

**整改：** 改为“双方都愿意再见”的当前意愿复核，不创建新关系等级。

### P1｜Pair Score 把“信号强度”和“路由公平”混成一件事

旧版一方面说 Mutual 最强，另一方面“从未互动”权重又可能比 Personal 更高，容易被误读成“系统认为陌生 pair 更喜欢彼此”。

**整改：** 明确 `Routing Score = Coverage + Signal - Cooldown`，路由分只决定下一轮互动机会，不代表兴趣概率。

### P1｜隐私生命周期不够明确

题库涉及“谁选择谁 / 谁愿意再见谁”的敏感关系数据，旧版只说“推荐不保存单向结果”。

**整改：** 默认 Session-only；秘密原始选择计算完成即删除；Session 结束清空关系图和 MATCH；默认不上传第三方分析。


### P1｜真心话与指人游戏出现“只差一个动词”的换皮题

跨题库相似度复核发现，若真心话只问“你选谁”，会与指人游戏的“你指谁”高度重叠。

**整改：** 真心话3～4档统一补上“为什么 / 哪个具体瞬间 / 你真实怎么判断”的披露要求；指人游戏继续保持快速公开选择。

### P1｜用户题面混入开发说明

终局卡曾把“不形成 MATCH / 不创建新等级 / 无交集 fallback”等实现说明直接写进题面，玩家体验会显得像调试界面。

**整改：** 题面只保留玩家要回答 / 执行的内容，实现规则迁移到逐卡元数据。

### P1｜扩圈模式复用了主线5档语义

扩圈模块原表头同样写“3～5档”，容易让开发者误以为扩圈5档也属于“双向关系确认”。

**整改：** 改名为“最低开放度”，明确这里只是解锁门槛，不参与主线 Relation Stage。

## 四、V1 / 初版 V2 迁移时必须删除的逻辑

1. 删除 `INTENSITY_WEIGHT = 1 / 2 / 4 / 8 / 16`。
2. 删除“4～5档固定占70%”约束。
3. 删除“全桌 H5”状态。
4. 删除“没有共同同意选项时自动换另一个动作”。
5. 删除把所有相同二选一答案都计 Compatibility 的逻辑。
6. 删除把“我从来没有：都没做过”计为 Shared 的逻辑。
7. 删除 `DOUBLE MATCH` 状态。
8. 删除所有秘密单向结果的长期持久化。

## 五、开发最低必须实现

1. `Intensity` 1～5 用户设置。
2. `Session Heat` H1～H4。
3. `Pair Unlock / matchRequired`。
4. Pair Cooldown 与低曝光补偿。
5. 异性 target pool 与不均衡人数归一化。
6. 私密选择流程。
7. MATCH 仅由双向秘密选择产生。
8. 当前动作级 consent。
9. Shared / Compatibility / Crowd / Personal / Mutual 的分离。
10. One-off Mutual Unlock 与 MATCH 分离。
11. 扩圈模式独立开关。
12. Session 结束时清理敏感关系状态。


## 六、外部原则交叉验证

本轮还用外部资料校验了核心机制：

- **互惠式自我披露**：关系研究长期支持自我披露与 liking / trust 之间的联系，因此真心话高档从“单边暴露”调整为双方轮流回答更合理。
- **眼神 / 距离只是行为线索，不是好感证明**：相关研究发现眼神、接近、交谈等行为与吸引存在关联，但不能据此把一次游戏动作直接推断成 MATCH。因此系统只记录明确选择，不通过动作自动推断喜欢。
- **同意必须自由、可撤回、具体且持续**：MATCH 不能替代当前动作的同意；拒绝后也不能自动换一个“轻一点”的动作继续问。
- **数据最小化**：秘密选择和关系信号只应保留完成当前 Session 所需的最小信息，单向结果尽快删除。

## 七、验收结论

经过第二轮交叉复核，V2 的主要结构冲突已经消除：

- **Session Heat 与 Pair MATCH 不再混用；**
- **5档重新收敛为真正需要双向条件的内容；**
- **七种玩法职责进一步去重；**
- **Shared / Compatibility 的统计偏差被修正；**
- **同意 fallback 不再自动替玩家做决定；**
- **开发端终于有逐卡元数据可执行。**

当前版本可以作为下一轮 SDD / 开发实现的稳定内容基线。
