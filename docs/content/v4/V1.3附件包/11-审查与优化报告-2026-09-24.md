## 三、达到预期的部分（确认有效的设计）

### 3.1 关系管线完整，档位语义与玩法职责对齐

- 7 种玩法职责互斥表（00-总览第二节）+ "审题最高规则"有效防止了换皮题；实测跨题库抽查未发现"只差一个动词"的重复。
- 档位衡量"关系暴露程度"而非"动作大胆程度"（"击掌=1–2 档、互选对象=4 档"），这是全套设计最有价值的一个决策，保证了酒吧场景下的得体性。

### 3.2 五层信号体系科学，防误判设计到位

- Shared / Compatibility / Crowd / Personal / Mutual 分层 + 各自封顶（00-总览第八节），路由分与好感概率彻底解耦。
- 三处防污染设计均有研究依据且已落实到 JSON notes：≥80% 共识题不计信号、"都没做过"不计共同经历、行为线索（对视/靠近）不自动推断好感。
- 单向选择不公开、不用于起哄、算完即删——这是同类产品普遍缺失的隐私底线。

### 3.3 同意与安全体系超出预期

- 动作级同意（同意牵手≠同意拥抱）、无交集直接跳过不自动替换、拒绝后不得"轻一点再问一次"、醉酒降档——四条规则互相咬合，覆盖了酒吧场景主要风险。
- 6 张身体接触卡全部带 mutual-current-consent + physical-contact 标签，元数据与规则一致。

### 3.4 题面梯度实测有效

- 真心话 1→4 档实测读感："注意细节 → 欣赏点 → 谁越聊越有意思 → 约咖啡最希望是谁"，梯度自然，无跳档。
- 指人游戏 3 档 #19"只能继续和一位异性聊十分钟"到 4 档 #36"只能留下一个联系方式"，信号强度递进合理。
- 全库无露骨、无外貌羞辱、无灌酒诱导；扩圈模块"不索联系方式、拒绝即止"执行到位。

## 四、发现的问题与改进建议（分级）

### P0-1｜MATCH 触发链路不闭环：5 档内容存在"永远玩不到"的时序风险

**问题**（最重要的一条）：

全库只有 **2 张卡**能创建 MATCH：`PN-NHIE-050`、`PN-POINT-050`（均为 50 号终局卡）。而 40 张 5 档卡（真心话 41–50、大冒险 41–50、二选一 43–50、默契 41–50）全部 `matchRequired=true`，即**必须先有 MATCH 才能出现**。

由此产生两个连锁问题：

1. **触发机制无规格**：00-总览第七节说"进入 H3～H4 后，系统可以在自然节点触发秘密选择"，但这是一句设计意图，没有落成任何规格——触发时机是什么（第几张卡后？H3 达成后多久？）、可否多次触发、系统级秘密互选与两张终局卡是什么关系（是抽这两张卡，还是独立 UI 流程），元数据 notes 与 09"开发最低必须实现"均未定义。抽卡规则（00-总览第九节）只说"剩余合法卡中随机"，**没有终局卡必出保障**。
2. **时序悖论**：若 MATCH 只能靠终局卡形成，则 MATCH 达成时游戏已接近尾声——38 张非终局 5 档卡（双人真心话、牵手/拥抱、MATCH 专属二选一/默契）**几乎没有出场窗口**，5 档体系名存实亡。

另：`PN-MOST-050` 的 postAction = `offer-one-paired-card-if-mutual`（全桌投票选出一对后，若双方愿意则提供一张配对卡）是第三个 MATCH 相关入口，但流程语义同样未定义。

**整改建议**：

1. 在 00-总览新增"秘密互选调度规则"一节：系统级秘密互选从 **H3 中段**（如完成 8–10 张有效卡后）即可首次触发，之后每完成 N 张（建议 5±2）可再次触发；触发方式为系统弹出的私密问题（即总览第七节那句题面），**不依赖任何卡片**。
2. 定义终局卡调度：Session 进入最后 25% 时，保证每游戏 50 号终局卡优先入池（或在结算阶段统一执行），避免终局卡被随机抽卡饿死。
3. 定义 `offer-one-paired-card-if-mutual` 的完整流程：投票结果 → 询问被投双方是否愿意（私密）→ 双方愿意才解锁一张 5 档双人卡；单方不愿意则当无事发生。
4. 明确：MATCH 形成后，该 pair 的 5 档专属回合才进入候选池（现有第九节"5档 70% / 4档 30%"已写，保留即可）。

### P0-2｜扩圈模式 40 张卡没有元数据，fallback 无法实现

**问题**：`10-卡片元数据.json` 只含主线 350 张。扩圈 40 张恰恰是最需要 `fallbackPolicy`（陌生人拒绝 → 立即执行本桌替代版本，不再二次邀请）和 `boundaryTags` 的模块。09 交付范围声称"逐卡开发元数据"，实际扩圈缺失，开发无法可靠实现"拒绝即切换"的硬规则。

**整改建议**：为 40 张扩圈卡补一份精简元数据（可放同一 JSON 或独立 `10b-扩圈元数据.json`），每张至少包含：`cardId / 最低开放度(3|4|5) / responseMode=public / consentMode=skip-anytime / signalEffects=none / fallbackPolicy=switch-to-table-version / boundaryTags=[]`；并注明扩圈卡永不进入 Pair Score 与 MATCH 计算。

### P1-1｜Coverage Gate 的"合格异性互动"无判定标准，H1–H2 可能卡节奏

**问题**：00-总览第三节 Coverage Gate 要求"进入 H3 前每位活跃玩家至少完成 1 次合格异性互动"，但什么算"合格"没有定义——真心话 1–2 档（系统指定异性 + 评论）算吗？大冒险 1–2 档（同步模仿动作，双方未必有定向互动）算吗？谁最可能/二选一（全桌题）显然不算。同时 H1+H2 合计仅约 7 张卡，若其中多张是全桌题，4–5 人局可能出现"卡在 H2 无法进 H3"的节奏停滞。

**整改建议**：在 00-总览明文定义：`targetMode ∈ {system-opposite-sex, choose-opposite-sex, system-pair, signal-pair, match-pair}` 且发生了实际应答/动作的卡 = 合格互动；并在调度规则中加一条下限——**H1–H2 期间每 3 张全桌题至少插入 1 张定向题**（或等价的定向题占比 ≥40%）。

### P1-2｜二选一私密卡参与 Compatibility 计算，与隐私原则有张力

**问题**：`PN-EITHER-041/042`（4 档私密选择）与 `PN-EITHER-050`（终局多选）的 signalEffects 均含 `compatibility`。Compatibility 需要跨题累计（至少 3 道有效共同题），意味着**私密答案要保存到 Session 结束并转为 pair 关系数据**，与总览"原始秘密单选计算后立即丢弃"的精神存在张力，且"散场后继续联系 VS 现在多聊"这类答案被转成关系数据可能超出用户预期。

**整改建议**：二选一私密卡（41/42/50）改为 `signalEffects=[]`，答案仅用于当轮展示；Compatibility 只由公开二选一（1–3 档 + 4 档公开题）计算。

### P1-3｜heatMin / heatMax 字段退化，无信息量

**问题**：脚本实测 350 张卡全部满足 `heatMin = intensity、heatMax = 4`。两个字段完全由 intensity 派生，等于冗余；"H4 时不出现破冰卡"目前只靠抽卡带宽表（软权重）保证，元数据层无硬约束。

**整改建议**（二选一）：

- 方案 A（推荐）：给低档卡设置真实 heatMax——1 档卡 heatMax=2、2 档卡 heatMax=3，让"过热不出破冰题"成为元数据硬约束，与带宽表双保险；
- 方案 B：在 JSON notes 声明"heatMax 恒为 4 是刻意设计，后期降温由带宽表权重控制"，避免开发误读。

### P1-4｜谁最可能 1–3 档个人票去向未定义

**问题**：1–3 档谁最可能是"投一个人"（signals=∅，合理），但"个人得票"是否落库、是否展示历史票型没有说明，开发可能自行发挥。

**整改建议**：在 03-谁最可能执行规则中加一句："1–3 档个人票仅当轮展示、用于气氛，不写入任何关系数据；只有 4 档 Pair Vote 产生 Crowd Signal。"

### P1-5｜大冒险 3 档座位类与靠近类的 consent 判定标准不一致

**问题**：`PN-DARE-019/024`（选人坐到旁边）consentMode=skip-anytime；`PN-DARE-029/030`（面对面渐进靠近/对视）=mutual-current-consent。直觉上"直接坐过去"对个人空间的侵入不弱于"渐进靠近"，两者判定标准相反，开发与玩家都会困惑。

**整改建议**：在 02-大冒险执行规则写明判定标准，例如："座位移动属于公开空间动作（skip-anytime）；面对面靠近、对视 + 距离协商、任何可能进入对方私人距离的动作（mutual-current-consent）"，并按此复核 19/24 是否需要改标签（若认定"坐旁边"=公开动作，现状可保留，但必须写明标准）。

### P2-1｜大冒险 1–2 档全是同步模仿类，酒吧氛围感不足

**问题**：1–2 档共 18 张全部是"同时比数字/摆姿势/模仿动作/镜像"类客厅游戏。破冰有效，但在成年酒吧局里偏幼稚，且与"把语言变成行动、产生关系变化"的玩法职责关联弱（signals=∅ 是对的，但 18 张全空窗使大冒险在半场内对关系引擎零贡献）。

**整改建议**：替换约 1/2（8–10 张）为酒吧场景轻互动：举杯致意并说一句祝酒词（对 TA）、互相用一句话介绍对方给全桌、碰杯时各说一个今晚的观察、并肩看一眼吧台并交换一句评论等。保持无身体接触、1–2 档语义不变。

### P2-2｜4 档高同质库存：指人 19 张、谁最可能 20 张

**问题**：指人 4 档 #31–49 句式几乎全为"指一个……的异性"；谁最可能 4 档 20 张全为"哪两个人……"。单局抽取量下（每玩法约 5–8 张）尚可接受，但语义梯度区分度低（"最想再见 / 最想收到消息 / 最想 MATCH"对被指者几乎等价），连抽两张即有明显重复感。全库 4 档 100 张（28.6%）也使中后段体验密度偏高。

**整改建议**：① 4 档题面做场景锚点改写（散场时 / 明天收到消息时 / 下次见面时——部分已有，扩大覆盖）；② 或结构性压缩：指人 4 档 19→15、谁最可能 4 档 20→16，各补 3–4 张到 3 档，缓解 H3 池深度（3 档现仅 82 张）。

### P2-3｜我从来没有 4 档"今晚限定"脱离玩法句式

**问题**：#41–49 从"我从来没有……"变成"你有没有……"，玩法身份一致性受损（玩家视角变成一般问答）。

**整改建议**：改写回原句式即可，语义不变，例如："我从来没有今晚特别注意过某个人笑起来的样子""我从来没有在游戏还没结束时，就希望散场后还能和某个人继续聊"。

### P2-4｜小局（4–5 人）Pair 路由分差过大

**问题**：4 人局仅 4 个异性 pair、5 人局 6 个。MATCH +5 的 Signal Bonus 在 4 个 pair 的小池中近乎锁死后续配对（次高分 Coverage +3 也追不上），可能出现"剩下半场几乎全是他俩"，与 Coverage Gate 的公平初衷相悖。

**整改建议**：Signal Bonus 按 pair 池规模缩放（如池内 pair 数 ≤6 时 MATCH=+3、Personal=+1），或将 Cooldown 对 MATCH pair 放宽为 3 轮；在 00-总览第八节补一句"小池校准"说明。

## 五、对照产品目标的预期效果评估

**目标：酒吧 4～5 人局中，增进男女互动氛围与关系。**

| 关系阶段 | 支撑机制 | 预期效果判断 |
|---|---|---|
| 破冰（不尴尬） | 三路破冰：内向者走谁最可能/二选一（全桌低暴露），外向者走大冒险（动作），定向者走真心话 1 档 | ✅ 好。不同社交风格都有低压力入口 |
| 注意 → 了解 | 真心话 1–2 档定向观察 + 我从来没有共同经历探测 | ✅ 好。互惠披露有研究支撑（09 第六节引用属实） |
| 好感试探 | 指人 3 档 + 二选一 3 档 + 默契预测 | ✅ 好。"公开选择"是暧昧催化剂，梯度自然 |
| 暧昧 | 指人 4 档 19 张 + Pair Vote 20 张 + 大冒险 4 档靠近/对视 | ⚠️ 中上。题量足但同质化（P2-2），全桌起哄与个人暴露的节奏交替需靠玩法轮换保证 |
| 双向确认 | MATCH + 5 档专属内容 | ⚠️ **风险点**。机制设计优秀，但触发链路不闭环（P0-1），不补规格则该阶段实际体验会缺失 |
| 愿意继续认识 | 终局复核卡（5 张 50 号） | ✅ 好。"只显示共同结果"的收尾体面且克制 |

**总体判断**：机制层面对"关系自然推进"的设计意图完成度约 85%；题面层面文案质量高、得体性好；最需要警惕的是 **MATCH 时序问题**——它决定了产品最高潮的体验（互选成功 → 解锁专属内容）是否真的会发生。修完 P0 两项后，该题库足以支撑一局 45–90 分钟、节奏完整的酒吧社交体验。

## 六、行动清单（按优先级）

**进入开发前必须完成（P0）**
